Finding P2: repeated sticky-fault receive remains quadratic.
Location: runtime/src/task.rs:436-437 (primary fault receive calls drain), 420-422 (drain always sweeps), 348-350 (HashMap retain).
A scope can join a fault while retaining n LIVE handles whose values were not received. Each later receive enters the primary branch, drains an already-empty JoinSet, then scans the entries HashMap; the current task only becomes abandoned when the receive future returns. Even as old entries retire, retain walks map capacity. n receives cause n scans of O(n) retained capacity. This contradicts any broad claim that receive retirement is now linear across all modes, although healthy record/receive/discard paths have the intended constant per-ticket work. No lifecycle semantics failure is established by this finding.

Reproduction: python3 /tmp/nagi-run.py /tmp/nagi-s1-independent-review/sticky-retirement-cost.log cargo run --offline --release --manifest-path /tmp/nagi-s1-independent-review/public-counterexamples/Cargo.toml --bin fault-retirement-cost
Release current-thread runtime, three repeats, child spawn/join excluded from timer. Medians: sticky receive 128=46,289ns; 1024=1,284,534ns; 8192=97,300,511ns. Sticky discard comparison 128=16,087ns;1024=115,892ns;8192=1,210,761ns. These are short microbenchmarks, not production latency estimates; the structural repeated retain establishes the asymptotic issue. Current author cost evidence measures healthy receive/discard and one bulk fault drain, so it misses this repeated receiving mode.

Recommendation: avoid full entries sweeps for every sticky receive, retire the failed current ticket after appropriate abandonment, preserve the explicit join/drain sweep for externally dropped handles as needed, and add this mode to the cost oracle. Any change must retain actual joins and cancellation-safe cause publication.
