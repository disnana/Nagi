# Nagi LTS候補の運用案

[English](lts-candidate.en.md) · [候補の検証記録](lts-candidate-validation.md)

2026-10-25時点の**未採用の提案**。0.2.2をLTSと決定したものではなく、サポート期間の対外的な約束でもない。現在の正式compilerは0.2.1。0.2.2の版更新、タグ、正式公開は本作業に含めない。

## 小さく維持できる範囲

初回は通常1系列だけを保守し、正式なLTS指定日から**6か月**を候補とする。延長は自動で行わず、終了前の稼働実績・依存更新・担当者の稼働余力から別途判断する。次のLTSへ移る場合に限り、追加の保守資源を確認・承認した上で、旧系列の残存期間内に最大3か月・最大2系列の移行重複期間を設ける案とする。資源がなければ重複期間は設けず、新系列の開始を調整する。新系列の公開だけで旧系列の終了日を早めない。

指定前に、保守責任者と代行者、依存監視・4 OS検証を続ける資源、開始日・終了日、配布対象をレビューで確定する。資源が確保できない場合は通常の安定版として扱う。年単位のサポートや常時対応のSLAを先に約束しない。

## 互換性を守るもの

- 指定時点の公開High/Low構文・型・所有権・capabilityの意味、公開標準API、文書化したCLI/project設定、正常入力の観測動作を基準にする。既存の移行済み契約を0.2.0以前へ戻す意味ではない。
- `build/run`の既定release、`--runtime-profile full`既定、完全検査、Cargoのnative freshness判定、lock整合性、旧成功exe保護を維持する。auto、生成本体CAS、unitsのopt-inを既定化する変更は開発系列へ送る。
- 元の`nagi-runtime`の公開Rust API（no-default-featuresを含む）と、適合が検証されたcompiler/runtimeの組合せを保つ。手書きRust依存や別版runtimeの任意の混在は保証しない。
- 配布対象は検証済みのLinux x86_64、Windows x86_64、macOS ARM64/Intel。Rust最低版、OS前提、TLS/native依存を指定時に固定し、更新後も最低版と配布検証を実行する。Rust ABIや任意の外部crateの互換性は保証しない。
- 内部IR、生成Rustのレイアウト、cache内容、非公開実装は安定APIにしない。cacheは不一致なら再生成し、安全性が証明できない最適化はfullへ戻す。永続データ形式を変更する修正には移行・バックアップ・失敗時の方針が必要。

JetBrains/VS Codeは独立した版で提供する。対応IDE/compilerの組合せと必要な機能検出を別表にし、compiler LTS指定からIDEの将来版対応を推測しない。IDEが送るflagは実compilerの対応を確認する。

## 修正とバックポート

LTS側は、到達可能性を確認したセキュリティ問題、誤コンパイル、データ破損、crash/hang、公開契約の回帰、必要な依存・配布互換性修正に絞る。新構文、広範囲のAPI、cache/query設計変更、実験的性能機能はmainの開発系列へ分離する。性能修正も同条件の計測と回帰が揃い、動作の危険を増やさない小差分だけを候補とする。

通常はmainで再現・修正・回帰を確認した後、`lts/<series>`へ最小差分をバックポートする。緊急の非公開修正では現行の[非公開報告方針](../../SECURITY.md)に従い、公開前の詳細をIssue/PRへ出さない。新たな応答・修正期限は設定しない。advisoryの存在だけでNagiの悪用可能性を断定せず、実lock版、features、呼出経路、配置条件を確認する。未確認は未確認として残し、「脆弱性ゼロ」とは呼ばない。

各修正は対象版、元commit、適用しない系列と理由、再現、High/保存Low/nativeの必要な回帰、独立レビュー、最新HEADのCIを記録する。依存更新もCargo.lockを伴い、通常・最適化経路、最低Rust、4 OSのL3で配布候補を検証する。検査の削除・skip追加・合否緩和で通さない。

安全性と互換性が両立しない場合、無言で契約を変えず、影響・緩和策・移行を示して個別の承認へ進める。互換な修正ができない問題を隠してLTSを継続したことにしない。利用者のアプリ固有Cargo.lockと既存exeはcompiler更新だけでは更新されないため、再解決が必要な条件と再ビルド手順も通知する。

## 開発系列と終了

LTS指定後は`lts/<series>`を修正系列、mainを次期開発系列とし、配布ページ・Docs・AI guideで版を区別する。これらのbranch作成・公開設定変更は本提案では実施しない。新機能のバックポートを断る理由と代替版を明記する。

終了日は指定前に合意する。終了の少なくとも30日前に再案内し、最終patch、残る既知問題、次系列への移行手順を整理する案とする。延長が未承認なら期間は延びない。終了後も非公開報告窓口は現行方針に従うが、旧系列への修正配布は約束しない。保守不能が判明した場合は隠さず早期に公開判断を求め、既存の約束を単独で短縮しない。

## 指定の可否

L3成功は必要な配布検証であり、LTS運用能力や長期安定性の証明ではない。[検証記録](lts-candidate-validation.md)の完了・未確認を根拠に、少なくとも次を別途承認する。

1. 最終版の4 OS/MSRV・browser/TLS・配布・install/upgrade/uninstall・既存security/互換性gateが成功し、代表例のfull/auto/保存Low/nativeが一致すること。
2. build、実行、test、CI時間を別指標で示し、改善しない場合・fallback・未測定を説明できること。
3. 既知のWindows/SF06等の失敗履歴に担当と調査結果または明示した残存リスクがあり、再実行成功だけを根因修正としないこと。
4. 公開Docs/SECURITY/IDE版表の古い状態記述を整合し、対応範囲、担当、サポート期間、終了条件を確定できること。

この条件が揃うまでは「LTS候補」とし、0.2.2通常版の可否とLTS指定の可否を別々に判断する。
