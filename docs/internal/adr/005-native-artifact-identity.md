# ADR 005: 共通ビルドキャッシュと実行ファイルの識別

状態: 採用。#76のCI失敗から判明したP1を修正する。言語の構文・型・実行時意味論は変えない。

## 問題

Cargoのtarget directoryは依存ビルドを共有する場所であり、生成したアプリごとの専用ディレクトリではない。`NAGI_NATIVE_TARGET_DIR`を指定しなくても、単独ファイルは作業フォルダーの`native-target`、プロジェクトは`build/native-target`を共有する。

従来は明示的な環境変数がある場合だけ、canonicalなソースと生成先を実行ファイル名へ反映した。既定経路では同じstemから同じpackage名を作る。そのため別の`main.nagi`を別の生成先でビルドしても、同じキャッシュ内の実行ファイルを上書きできた。Cargoのロックはビルド終了後に解放されるので、先の`nagic run`が後のアプリを実行し得る。

## 契約と採用案

- 既定・明示のどちらのtargetでも、canonicalな入口ソースと生成ディレクトリの組をpackage/executable名へ反映する。既存の16桁識別子を両経路で使う。
- 等価なパス表記は同じ識別子になる。別のソースまたは生成先には別の名前を割り当て、依存のキャッシュは共有する。
- target directory、生成ソースの場所、実行時のproject working directoryは変更しない。実際の実行ファイルは`native:`行で知らせる。
- 同じ生成先への同時コンパイルには対応しない。同一ソース・生成先に対する競合や、そのファイルの同時編集をこの修正で隔離するわけではない。

識別子は短いハッシュであり、暗号学的な隔離や権限の仕組みではない。別compiler版をまたいだ名前の固定も公開契約にしない。配布先で安定した名前が必要な場合は、ビルドが示した実行ファイルを選び、配布時に命名する。

## 互換性

未リリースの変更。環境変数を指定しない場合も、`nagi-main`から`nagi-main-<識別子>`へ名前が変わる。古い版の固定名を使うスクリプトは、`native:`行または生成Cargo.tomlのpackage名から実際のパスを取得する。`nagic run`と、実際のパスを利用する既存エディター・配布スクリプトはそのまま動く。

「共有時だけ識別する」という以前の方針を、環境変数の有無ではなく、実際に共通キャッシュへ置く全アプリに適用する。既定の固定名を維持するより、別アプリの実行を防ぐ規則を優先する。

## 不採用案

| 案 | 不採用の理由 |
|---|---|
| テストのcwdを分けるだけ | テストの衝突は消えるが、利用者の同じビルド経路は壊れたまま |
| 最初に使ったアプリだけ固定名にする | 実行順や過去のファイルに判定が依存し、決定的でなくなる |
| 特定のソース配置だけ固定名を許す | 同名ソース、別生成先、aliasの例外規則が増える |
| ソースごとにtargetを分ける | 依存のキャッシュを分断し、ビルド費用と出力先を変える |
| 独自ロックをrun終了まで保持する | アプリの実行時間だけ別ビルドを止め、Cargo以外の調停も必要になる |

## 継続検査

`compiler/tests/shared_target.rs`で、第一アプリのCargoビルドが終わってロックを解放した後に第二アプリをビルドし、第一の実行を再開する。環境変数を除いた既定経路と明示共有の両方で、各stdout・別実行ファイル・同じtarget親を検査する。等価なパス表記と別生成先も確認する。

`compiler/tests/project.rs`では既定project target、識別子付き実行ファイル、元projectのworking directoryを確認する。Auth等の実Cargoテストも、既定キャッシュで再実行する。並行生成の順番やsleepだけに依存したテストにはしない。
